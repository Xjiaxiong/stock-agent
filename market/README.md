# 每日盘面复盘 Agent（第一步：情绪指标）

目标：每天用真实市场数据判断**市场阶段 → 热点板块 → 风格 → 机会点 → 操作手法**。

当前进度：**情绪指标 + 板块强度 + LLM 每日复盘报告均已可用**，并已接入后端与前端。

## 目录

| 路径 | 作用 |
|---|---|
| `data/hithink.py` | 数据层：同花顺盘面接口取数（涨停池/跌停池/炸板池/天梯/异动/热榜/板块） |
| `indicators.py` | 计算层：全市场 → 客观指标（纯函数，可单测） |
| `daily_snapshot.py` | 编排：取数 → 算指标 → 落盘 → 生成可读简报 |
| `daily_review.py` | 判断层：把指标交给 LLM，产出《每日复盘与明日计划》 |
| `snapshots/` | 每日快照（`{日期}.json` 完整数据、`{日期}.md` 简报、`latest.json`） |
| `reports/` | 每日复盘报告（`{日期}.md` 可读报告、`{日期}.json` 结构化结果） |

## 怎么跑

```bash
cd ~/Desktop/LEARN/self-projects/stock-agent

.venv/bin/python market/daily_snapshot.py                  # 今天
.venv/bin/python market/daily_snapshot.py --date 2026-09-11
.venv/bin/python market/daily_snapshot.py --show           # 只看输出不写盘
.venv/bin/python market/daily_snapshot.py --full           # 全市场全量采样（更慢更准）

# 每日复盘（LLM 判断层）
.venv/bin/python market/daily_review.py                    # 复用当天快照
.venv/bin/python market/daily_review.py --fresh            # 重新采集后再复盘
.venv/bin/python market/daily_review.py --date 2026-09-14
```

前提：项目根目录 `.env` 中已配置 `HITHINK_FINANCE_API_KEY`。

## 通过接口/前端使用

```bash
# 当前可复盘的最新交易日（前端进页面时用它预填日期）
curl -s http://127.0.0.1:8000/api/daily-review/latest
# -> {"trade_date":"2026-09-15","note":"","today":"2026-09-15"}

# 后端 SSE 接口（本地）
curl -N -X POST http://127.0.0.1:8000/api/daily-review \
  -H 'Content-Type: application/json' \
  -d '{"date":"2026-09-14","fresh":false}'
```

SSE 事件顺序：`meta`（这次实际用哪一天 + 为什么）→ `progress`×3 → `report`。
`report` 事件里除了 Markdown 报告，还带一份 `card` 结构化摘要（市场阶段/一句话结论/
四个关键数字+环比/核心依据/热点板块/核心龙头/明日应对/风险），前端用它画"分享卡片"，
导出成一张 PNG。

前端页面：`http://localhost:3000/daily`（首页也有入口）。进去会先问
`/api/daily-review/latest`，把日期框填成"最近一个已收盘的交易日"，所以 9/15 早上
点复盘拿到的是 9/14 的盘面，并会在页面上写明用了哪一天。

报告出来后页面顶部会出现**分享卡片**（Canvas 手绘，所见即所得），支持：

- 下载图片：`每日复盘_2026-09-15.png`，1080 宽、2 倍图，高度按内容自适应；
- 复制图片：直接粘贴到微信/钉钉等聊天窗口；
- 复制文字：文字版结论（阶段 + 一句话 + 关键数字 + 热点 + 应对）。

版式与配色都在 `frontend/lib/shareCard.ts`，市场阶段决定卡片主色
（退潮期红、主升期绿、修复期橙、冰点期灰蓝、分化期紫）。

> 部署注意：Vercel/Render 的后端若只打包 `backend/` 目录，`market/` 不会随之上传，
> 该接口会返回"每日复盘模块不可用"。需要线上可用时，要把 `market/` 纳入部署范围
> （例如把后端项目根目录设为仓库根，或把市场复盘模块移入 `backend/`）。

## 指标口径

**情绪周期**：涨停/跌停/炸板家数、封板率（封住 ÷（封住+炸板））、首板数、连板家数、最高连板、连板梯队分布。

**市场活跃度**：涨跌家数分布、上涨占比、平均涨跌幅、成交额（基于采样外推）。

**热点题材**：把涨停原因按 `+`/`、` 拆成标签聚类，按"多少只不同股票挂了该标签"排序
（广度优先 + 连板高度加成），避免同一只票的多个概念标签霸榜。

**资金风格**：早盘封板占比、大封单家数、3 板及以上家数、ST/新股涨停数，用透明规则给出
"连板题材 / 趋势普涨 / 结构性"初判。

**跨日**：与上一份快照对比得到环比变化；用昨日涨停名单计算今日延续率（赚钱效应）。

**板块强度**：把同花顺概念指数快照（涨跌幅）与涨停原因聚类**交叉验证**——只有"指数上涨
且板块内有涨停股"的题材才算共振热点，并给出涨停数、最高板、龙头、连续上榜天数。
连续天数依赖 `snapshots/` 里已保存的历史快照（缺哪天就断在哪天）。

**核心龙头**：先按关键词把涨停原因标签聚成"同链"（半导体硅片 / 半导体设备 / 半导体材料
→ 半导体），链内按 `身位（连板数）> 板别 > 首封时间 > 封单额` 排序：身位最硬，同身位时
10cm（主板）优先于 20cm（创业板/科创板）——主板那只才是资金定价的主锚，20cm 是同题材的
弹性方向，所以同链会分别给出"10cm 龙头"和"20cm 龙头"。链间按
`最高板 × 3 + 链内涨停家数 × 2` 排序取前三条。一只票只归给最强的那条链，避免重复出现。
另外给出每只龙头的**特征词**（同花顺涨停原因标签，回答"它靠什么涨"）。
结果同时进分享卡片和报告正文的"核心龙头"小节。
通用词（增长 / 材料 / 设备 / 高端 / 拟收购…）不参与同链合并，否则会把不相干的题材缝成假主线。

## 测试与 CI

指标层是纯函数，直接单测（不联网、秒级跑完）：

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest   # 30 个用例：情绪/广度公式、板别判定、龙头同链合并与排序、报告与卡片契约、事实校验
```

`.github/workflows/ci.yml` 在 push / PR 时跑两件事：`pytest` 与前端
`tsc --noEmit` + `eslint`。测试刻意只覆盖"能确定性复算"的部分（指标、口径、字段契约），
LLM 输出质量不放进 CI，改用下面的"数字校验"兜底。

## 观测与事实校验

- **LLM 用量日志**：所有调用统一走 `market/llm_client.py`（重试/超时/失败都记一笔），
  写 `market/logs/llm-usage.jsonl`（可用 `LLM_USAGE_LOG` 改路径）；
  `GET /api/metrics` 返回调用次数、成功率、平均/最慢耗时、token 合计与最近几次调用。
- **数字校验**：`market/verify.py` 把 LLM 正文里的盘面统计数字（家 / % / 亿 / 万 / pct）
  逐个回指标快照里核对（含"昨日 X 家 = 今日 X − 环比 delta"这类可推导值），
  结果写进 `result["fact_check"]`，报告末尾给一行结论；阈值型表述
  （"回升至 60% 以上"）不算断言，会跳过以免误报。实测 9/14~9/16 三天均为 100% 可复现。

## 数据边界（同花顺公开能力的硬限制）

- 分钟 K、tick、海外行情、宏观数据、新闻公告原文、研报原文**均不提供**。
- 个股所属行业/概念反查（"某只票属于哪些板块"）**尚未提供**，因此板块归属只能从
  涨停原因、板块指数成分股反向推断。
- **全市场行情快照只返回最新数据**，不接受历史日期：因此"涨跌家数分布"只能表示运行当天，
  历史交易日的该字段会带 `is_stale=True` 标记，报告中也会明确提示，不可当作当日分布使用。

## 数据就绪校验（防止"张冠李戴"）

涨停池接口在"目标交易日的数据还没生成"时会**静默回退到上一交易日**，跌停池则直接返回空。
如果不校验，凌晨跑 `daily_snapshot.py` 就会把昨天的盘面写成今天的快照（实测发生过：
9/15 凌晨生成的快照，涨停名单和 9/14 一字不差）。

于是有两层保护：

**一、入参解析（`hithink.resolve_trade_date`）**：把"用户要的日期"翻译成"真正能复盘的交易日"，
返回 `(交易日, 说明)`，说明会一路带到前端和报告里。

| 请求 | 解析结果 |
|---|---|
| 空 / 今天，且**未收盘** | 最近一个已收盘交易日（9/15 早上 9 点 → 9/14） |
| 空 / 今天，且已收盘（15:00 后） | 今天 |
| 周末/节假日 | 之前的最近交易日（9/13 周六 → 9/11 周五） |
| 明天/未来 | 报错"那个交易日还没到" |
| 上游还没生成数据 | 再退到上游最新可用交易日 |

注意**不能只看"上游有没有数据"**：上游在盘中就开始吐当天的涨停池/天梯，
那只是"进行中的半天"，收盘前拿来做复盘等于用半截数据下结论。

**二、取数兜底（`hithink.ensure_data_ready`）**：采集前用**连板天梯**（近 30 个交易日）
的 `date_list[0]` 作为"上游最新可用交易日"复核，目标日超过它就抛 `DataNotReady`，
CLI 退出码 2 且**不写任何文件**；日期不在交易日历里同样拒绝。

快照里会写入 `data_source.latest_ready_trade_date` 作为"出身证明"：之后读取已有快照时，
如果发现它是在 `latest_ready_trade_date < trade_date` 的情况下生成的，复盘会直接拒绝复用
（提示删除该文件重跑），避免拿错日期的数据去喂 LLM。

另外两点口径修正：

- 全市场分布的"数据日期"改用**上游最新可用交易日**，不再用接口返回的墙钟时间戳
  （凌晨跑会跨天，把昨天收盘的数据误标成今天）；历史回填仍会正常打 `is_stale` 标记。
- `snapshots/latest.json` 只在日期不倒退时更新，补跑历史交易日不会把最新指针指回过去。
  `reports/` 也改成统一落盘：CLI 和前端点击都会存档 `{交易日}.md` / `{交易日}.json`。
